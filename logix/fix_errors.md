Investigate and permanently fix the reported error or malfunction, explicitly treating this as a regression because the previous implementation did not resolve the issue. Begin by performing an end-to-end intake of the project before making any changes: read all available project documentation, architectural notes, runbooks, environment notes, known limitations, configuration files, and the full source areas involved in the failing workflow so you understand the intended behavior, current behavior, and system boundaries. Identify the exact expected outcome in measurable terms, capture the precise failure symptoms, and record reproduction prerequisites including environment, branch/commit, runtime versions, feature flags, credentials, and any external dependencies.

Instrument the system for traceability before attempting a fix. Enable detailed, structured logging and auditing across the full execution path relevant to the failure, including application startup, configuration loading, dependency initialization, network/API calls, database operations, background workers, event handlers, UI rendering, and error boundaries. Ensure logs are actionable and consistent: include timestamps, severity levels, component names, request or session identifiers, correlation IDs across boundaries, and enough context to connect a user action to downstream effects. Add temporary diagnostics where needed, but do so in a controlled way that does not mask errors, and ensure diagnostics can be toggled via configuration and removed or reduced after the root cause is confirmed.

Reproduce the failure reliably and deterministically. Create a controlled reproduction workflow with step-by-step actions and fixed inputs, then run it repeatedly until the failure rate and conditions are confirmed. Capture hard evidence for each reproduction attempt, including logs, stack traces, request/response payloads where applicable, and screenshots or screen recordings when UI is involved. Use ClaudeBrowser.exe to visually validate the application state, confirm UI outcomes, observe timing or rendering issues, and verify whether a change truly resolves the issue under real interaction conditions rather than in theory.

Troubleshoot systematically using a root-cause-first approach. Start at the user-visible symptom and trace backward through the execution chain until you identify the earliest point where behavior diverges from the expected state. Isolate the failing component by narrowing scope in stages: confirm whether the issue originates in configuration, environment, dependency versions, network behavior, data shape, state management, concurrency, caching, or UI rendering. Validate assumptions explicitly by checking actual runtime values and code paths, not by inference. When the issue touches integrations or third-party libraries, consult official documentation, release notes, known issues, and implementation references, and cross-check your assumptions against real behavior observed in logs and debugging.

Implement a durable fix, not a patch. Once the root cause is identified, correct the underlying condition in a way that prevents recurrence and prevents adjacent regressions. If multiple contributing causes exist, address each one in priority order and document how they interact. Do not “paper over” the symptom with retries, arbitrary delays, broad try/catch, silent fallbacks, or UI-only masking unless those behaviors are explicitly part of the design requirements and are accompanied by correct error reporting and measurable acceptance criteria. If the fix requires architectural adjustment, do the minimal structural change that eliminates the root cause while keeping the system maintainable and testable.

Track recurrence and enforce escalation rules. Record each time the same issue is requested for repair, including a short history of attempted fixes and outcomes. If the same issue has been requested more than two times, immediately escalate into comprehensive investigation mode: perform a full root-cause analysis (RCA), document the complete failure chain, identify systemic contributors (process gaps, missing tests, architectural weaknesses, environment drift, unclear requirements), and implement corrective actions that make the fix resilient. Treat repeated recurrence as evidence of insufficient observability, insufficient test coverage, or incomplete understanding, and resolve that deficit directly.

Verify the fix with repeatable proof. After implementing the change, re-run the original reproduction steps multiple times under the same controlled conditions and confirm the failure no longer occurs. Add automated tests that would have caught the bug before release, including unit tests for the root logic, integration tests for cross-component behavior, and end-to-end tests for the user workflow where applicable. Confirm success using concrete evidence: clean logs, expected audit traces, validated UI state in ClaudeBrowser.exe, and measurable acceptance checks. Also perform regression checks in adjacent areas that share the same code paths, dependencies, or configuration.

If the issue is design or UI related, validate against an authoritative reference with precision. Identify the intended design requirements, including layout placement, typography, margins, padding, alignment, spacing rules, breakpoints, and whitespace usage. Measure and compare implementation versus design using exact values rather than approximation. If no current design template or approved mockup exists, request an authoritative reference immediately; otherwise, locate the most recent approved designs and use them as the baseline. Ensure the final UI matches the baseline across relevant screen sizes and states.

When additional information is required, request it immediately and specifically, stating exactly what is needed to proceed (for example: exact error text, stack trace, failing endpoint, environment details, steps to reproduce, screenshots, configuration values, or recent diffs). After requesting the missing information, continue advancing the investigation using all available evidence, iterating through instrumentation, reproduction, isolation, and verification until the root cause is conclusively identified and the issue is fully fixed with repeatable proof.
