## 4. Fix DTO Mapper for camelCase API Responses

### What
The Continuum API returns camelCase field names (`startTime`, `endTime`, `isAllDay`) but the mapper expected snake_case. Events were silently losing field values.

### Root Cause
`CalendarEventDto` interface and `mapEventDto` function only handled snake_case keys. The actual API response used camelCase.

### Fix
Updated `mapEventDto` to use fallback accessors that try camelCase first, then snake_case:
```typescript
startDateTime: d.startTime || d.start_time || '',
isAllDay: d.isAllDay ?? d.is_all_day ?? false,
```

Updated `CalendarEventDto` interface to include both camelCase and snake_case property aliases.

### Files Modified
- `src/types/calendar/index.ts` — DTO interface and mapper function

## 5. Fix Delete Event Race Condition

### What
Deleting a calendar event appeared to succeed (dialog closed) but the event remained on the calendar. The delete API call was silently failing.

### Root Cause
`EventDialog` called `onClose()` synchronously after starting the async `onDelete()` call. The dialog closed and React unmounted the component, nullifying state before the delete API call completed. Any API errors were swallowed.

### Fix
- EventDialog now `await`s `onDelete()` before calling `onClose()`
- CalendarPage controls dialog closing only after successful deletion
- API errors are caught and displayed in the dialog's validation area so the user sees the failure
- calendarService `deleteEvent` changed from void to return boolean for success tracking

### Files Modified
- `src/components/calendar/EventDialog/EventDialog.tsx` — Async delete flow
- `src/pages/Calendar/CalendarPage.tsx` — Dialog close after success
- `src/services/calendar/calendarService.ts` — Delete return type

## Technical Notes

- **API Layer**: All calendar CRUD goes through `calendarService.ts` → `continuumClient` → InspireContinuum API (`/api/v1/outlook/events`). No direct database connections.

- **Recurring Event Strategy**: Events are stored as single records with recurrence metadata. The frontend expands them into individual occurrences within the visible date range using `expandRecurringEvents()`. This matches the WPF client-side expansion approach.

- **Reminder Architecture**: The `reminderService` runs as a singleton checking every 30 seconds. It receives the full event list from CalendarPage and evaluates which events are within their reminder window. This is identical to the WPF `CalendarReminderService` pattern.

- **Event Cache**: Uses a simple `Map<string, { events, timestamp }>` keyed by `${start.toISOString()}_${end.toISOString()}`. Cache entries expire after 5 minutes. Any write operation clears the entire cache.

- **DTO Resilience**: The mapper handles both camelCase (API reads) and snake_case (API writes) to prevent field mapping issues regardless of which format the API returns.
